# FUZIX on the IBM PC (Intel 8086 / 8088)

Deep-dive into how FUZIX ports to the **IBM PC family** — real 8086/8088 machines
with a BIOS. The generic memory model lives in
[ARCHITECTURE.md](../ARCHITECTURE.md#memory-model--banking); this file collects the
concrete, board-level facts for the `ibmpc` board. The 8086 CPU and the `ibmpc`
board are ported into `fuzix-new` under [`kernel/cpu/i8086/`](../kernel/cpu/i8086/)
and [`kernel/platform/ibmpc/`](../kernel/platform/ibmpc/), built with the
`ia16-elf` gcc toolchain (`cmake/toolchain-i8086.cmake`).

> The other i8086 board — the bare embedded **80C188** on the RC2014 bus (no
> BIOS, no PC peripherals) — is a very different machine and has its own writeup
> in [80c188.md](80c188.md). This file is the PC-specific half.

> **Status (2026-08): userland ships; the kernel now builds well past MM +
> context switch with the real toolchain, but still won't boot.** The
> **userland** (`lib` + `bin`) builds end-to-end with the real `ia16-elf-gcc`
> 6.3.0 — 234 programs as real MS-DOS/MZ executables — and is packaged into a
> mountable root-disk image (`diskimage` → `hd0.img`, see §6).
>
> The **kernel** used to only pass the *fake*-toolchain / `cc -E` checks; it now
> compiles substantially further with the real ia16 compiler after fixing the
> build glue and finishing the core paths:
>
> - **Link glue**: dropped `STARTUP(crt0.o)` from [`fuzix.ld`](../kernel/platform/ibmpc/fuzix.ld)
>   (our build passes crt0.o first explicitly), and added the missing
>   `${MEMALLOC_SOURCE}` compile so `_memalloc`/`_memfree` resolve.
> - **Context switch**: [`tricks.S`](../kernel/platform/ibmpc/tricks.S) was a broken
>   upstream sketch (used the non-existent `%ei` register, `calloutstring`, an
>   invalid `.bss` data section, dangling symbols). It is **rewritten** into a
>   real 8086 `switchin`/`plt_switchout`/`dofork` following the working
>   rcbus-8085 banked idiom — see §2 (Context switch). It assembles cleanly.
> - **MM**: [`mm/bank8086.c`](../kernel/mm/bank8086.c) now compiles — its
>   `pagemap_realloc` was ported from the stale 3-arg API to the current
>   `(struct exec *hdr, usize_t size)`, and `fork_copy` typos were fixed.
>
> The remaining **build** blockers are stale driver signatures (e.g.
> [`devtty.c`](../kernel/platform/ibmpc/devtty.c): `kputchar(char)` →
> `uint_fast8_t`, `tty_setup(minor)` → `(minor, flags)`) — the whole board is a
> pre-API-churn skeleton, so expect driver-by-driver signature drift. Beyond
> building, it still won't **run**: there is no real-mode **loader**, and the
> `CONFIG_SPLIT_UDATA` per-task udata/kernel-stack save/restore is undesigned
> (see §2 (Context switch)) — that needs an 8086 emulator to finish and verify. So the shipped
> image is still the **userland root disk**; the `diskimage` target does not
> depend on the kernel, so the userland deliverables build regardless.

## 1. Toolchain

x86 builds with the **ia16 GCC** cross toolchain (real-mode 16-bit), *not* the
Fuzix Compiler Kit or SDCC. This is the shared `i8086` CPU toolchain — the
embedded 80C188 board uses it too:

| Tool     | Program        | Notes |
|----------|----------------|-------|
| Compiler | `ia16-elf-gcc` | `-Os`, 16-bit real mode |
| Assembler| `ia16-elf-gcc` | `.S` via the compiler driver |
| Linker   | `ia16-elf-ld`  | ELF, linker script `fuzix.ld` |
| Objects  | `.o` (ELF)     | `BITS=16`, `EXECFORMAT=16` |

See [`cpu-8086/rules.mk`](../../FUZIX/Kernel/cpu-8086/rules.mk). Like `i8080`, the
executable format is the 16-bit loader (`syscall_exec16`), but the object
format and segmented model are entirely different.

## 2. Memory model

### Segmented real mode instead of bank switching

The 8086 addresses 1 MB via 16-bit **segment:offset** pairs. FUZIX doesn't need
external banking hardware — it uses the **segment registers themselves**. Each
process carries its own segments in the udata
([`cpu-8086/cpu.h`](../../FUZIX/Kernel/cpu-8086/cpu.h)):

```c
uint16_t cseg;   /* CS to use (code + udata store) */
uint16_t dseg;   /* DS/SS to use (data + stack)    */
...
extern uint16_t get_code_segment(uint16_t pv);
extern uint16_t get_data_segment(uint16_t pv);
```

A user pointer `uptr_t` is a **16-bit offset within a 64K segment**
(`uputp/ugetp = uputw/ugetw`). The kernel runs "small" (or tiny) at a low
segment; each process is a separate 64K code + 64K data/stack region reached by
reloading CS/DS/SS. This is **split I/D** (`CONFIG_SPLIT_UDATA`,
`syscall_exec16`).

### The 8086 page/segment manager ([`mm/bank8086.c`](../kernel/mm/bank8086.c))

`CONFIG_BANK_8086` selects a manager that treats up to **640K of RAM as 4K
"pages"**. For each process it finds a **pair of chunks** so that the stack
grows down from `0xFFFF` and data grows up from `0x0000`, with an arbitrary
hole in the middle; on collision it **rearranges memory** rather than using
ELKS/Minix-style `chmem`. Key points:

- Kernel is loaded in the lowest pages; `pagemap_init` is told the first free
  page and the total page count.
- Uses platform `copy_page` / `zero_page` to move far (possibly overlapping)
  blocks.
- 4K pages → a 640K PC is ~160 pages; a future 286 with a bigger `page_t`
  could map 16 MB (~4096 pages), marking the `640K–1MB` I/O/ROM region as dead.
- `pagemap_realloc(struct exec *hdr, usize_t size)` derives the split-I/D
  layout from the 16-bit a.out header — `csize=PAGES_IN(a_text)`,
  `dsize=PAGES_IN(a_data+a_bss)`, `ssize`=remainder of `PAGES_IN(size)` — since
  `syscall_exec16` doesn't split I/D itself.

`PROC_SIZE = 128` (a 64K segment = 128 × 512), `PROGBASE 0x8000`,
`PROGTOP 0xE000` (ibmpc).

### Extended memory: EMM and XMS

- **EMM** ([`platform-ibmpc/emm.c`](../../FUZIX/Kernel/platform/platform-ibmpc/emm.c),
  `CONFIG_IBMPC_EMM`): LIM expanded-memory boards (triple ports `208/9/A` or
  `218/9/A`). The manager can request a **64K EMM bank** per process
  (`emm_alloc_bank` → sets `m->emm` token and `m->dseg` page-frame,
  `emm_select`, `emm_free_bank`), so extra processes live in banked expanded
  memory beyond the 640K conventional limit.
- **XMS** ([`platform-ibmpc/xmsrd.c`](../../FUZIX/Kernel/platform/platform-ibmpc/xmsrd.c)):
  uses 286 high memory (>1 MB) as a **RAM disk**.

### Context switch ([`tricks.S`](../kernel/platform/ibmpc/tricks.S))

The platform supplies three CPU-level primitives (contract in
[`kernel/core/process.c`](../kernel/core/process.c)): `plt_switchout()` (give up
the CPU, never returns), `switchin(ptptr p)` (resume `p`), and
`dofork(ptptr child)` (returns the child pid in the parent, 0 in the child). The
8086 version follows the **banked idiom of the working rcbus-8085 port**: save
the ia16 call-saved registers (`si`, `di`, `bp`) plus flags, stash the kernel
`SP` in `udata.u_sp`, pick the next task with `getproc()`, then `switchin()`
restores that task's `SP` and register frame; `dofork()` saves the same frame,
calls the C `fork_copy()` to duplicate the bank, then `makeproc()`.

> **The unfinished part.** On the 8085 the udata *and* the per-task kernel stack
> live in the banked window, so a single bank select swaps them in for free. The
> 8086 is `CONFIG_SPLIT_UDATA` with **one** `udata` and **one** `kstack` in the
> common `kernel_ds`; changing user *segments* does **not** swap them. A true
> multi-task switch therefore needs an explicit per-task **udata + kernel-stack
> save/restore** — the store for those copies (the sketch's phantom `udata_ds`)
> was never designed. Until it is, `switchin()` only resumes the task that
> already owns the live udata (the `nready==1` fast path); a switch to any other
> task deliberately traps rather than run with the wrong udata/stack. The hook
> where `restore_udata`/`stash_udata` must go is marked in `tricks.S`. Finishing
> this needs an 8086 emulator to validate.

8086 assembly notes: the port is `.code16` + `.att_syntax prefix` with **bare**
ELF symbol names (no leading `_`, unlike `fcc`); rotate-by-immediate > 1 is a
186+ instruction, so on the 8086 use `rol $1` repeated or `rol %cl`.

## 3. Boot & image

The IBM PC boot flow (from [`README`](../../FUZIX/Kernel/platform/platform-ibmpc/README)
and [`bootstrap.S`](../../FUZIX/Kernel/platform/platform-ibmpc/bootstrap.S)):

1. The **boot sector** loads at `0x7C00` and pulls in the kernel image.
2. The image is relocated **down to low memory** (~`0x0500`/`0x0800`, the lowest
   place it fits, for small-memory machines).
3. The loader detects **CPU type, memory size, bus width, FPU** and posts an
   info structure.
4. It instantiates the 8086 banking module and jumps to the kernel entry with
   `CS/DS/ES/SS` set and interrupts off.

Proposed low-memory map:

```
0000-03FF   Interrupt vectors
0400-04FF   BIOS data page
0500-05FF   Interrupt stack   (kernel DS/ES/SS)
0600-07FF   Udata
0800-....   Kernel image (data, then code = kernel CS)
....-E000   Code
E000-EFFF   Discard
E000+       User space / more RAM (128K, 256K, 512K, 640K…)
A0000-FFFFF I/O and ROM (video, BIOS)
```

The kernel is linked to an ELF with an explicit script
([`fuzix.ld`](../kernel/platform/ibmpc/fuzix.ld));
[`platform-ibmpc.cmake`](../cmake/platform-ibmpc.cmake) lists the object order
(`crt0`, core, `bank8086`, BIOS drivers, …), mirroring the upstream `Makefile`
`image` rule.

## 4. Device drivers (IBM PC)

The PC port leans on the **BIOS** for disk and does the rest directly:

| Area      | Files | Notes |
|-----------|-------|-------|
| Disk      | [`biosdisk.c`](../../FUZIX/Kernel/platform/platform-ibmpc/biosdisk.c) | BIOS `int 13h` block I/O (floppy + HD) |
| Console   | [`bioscon.c`](../../FUZIX/Kernel/platform/platform-ibmpc/bioscon.c), `biosvid.S` | text video via BIOS; core **VT** layer (`CONFIG_VT`) with dynamic `vt_width × vt_height` |
| Keyboard  | `bioskey.S`, [`xt_key.c`](../../FUZIX/Kernel/platform/platform-ibmpc/xt_key.c) | XT/AT keyboard |
| Interrupts| [`8259a.c`](../../FUZIX/Kernel/platform/platform-ibmpc/8259a.c) | 8259A PIC |
| Serial/tty| [`devtty.c`](../../FUZIX/Kernel/platform/platform-ibmpc/devtty.c) | 8250/16550 serial |
| RAM disk  | `xmsrd.c` | XMS high-memory ramdisk (286) |

Design intent: use **interrupts directly** for timer, keyboard and serial, and
the **BIOS only for disk**; video is done directly (with the BIOS as fallback
for "weird non-PC" clones). `TICKSPERSEC 50`.

The [`ibmpc`](../kernel/platform/ibmpc/) board is an 8086/8088 real PC with a
BIOS: `bank8086` (640K in 4K pages) plus optional EMM/XMS. Its MM and context
switch build; it is blocked on stale driver signatures and then needs a loader.

## 5. How this is wired into `fuzix-new`

The `i8086` / `ibmpc` target is now in the tree. What it took:

1. an **ia16 GCC** toolchain file ([`cmake/toolchain-i8086.cmake`](../cmake/toolchain-i8086.cmake):
   `ia16-elf-gcc` / `ia16-elf-ld`, ELF `.o`, a `fuzix.ld` link script) — a
   second gcc-kind toolchain alongside PDP-11, and a third kind next to `fcc`;
2. the **segmented / `bank8086`** memory manager (selected by `FUZIX_MM=bank8086`,
   the default for `ibmpc`) plus `copy_page`/`zero_page` and split-I/D exec;
3. the CPU low level ([`kernel/cpu/i8086/`](../kernel/cpu/i8086/)) and the board's
   BIOS drivers ([`kernel/platform/ibmpc/`](../kernel/platform/ibmpc/)), linked in
   the order of the upstream `Makefile` `image` rule
   ([`cmake/platform-ibmpc.cmake`](../cmake/platform-ibmpc.cmake)).

The link produces an ELF image (`fuzix.elf`, no `objcopy` step). With the real
`ia16-elf-gcc` the kernel now compiles well past the MM and context switch; the
remaining build blockers are stale driver signatures, and to actually *run* it
still needs the real-mode **loader** plus the `CONFIG_SPLIT_UDATA` udata/kstack
save/restore (see the status note at the top and §2, Context switch) — so it is
still the least-finished of the ported kernels.

### Userland (`lib` + `bin`) — the part that builds for real

The i8086 **userland** is a full gcc-kind port (the second after `armm0`),
mirroring upstream [`Target/rules.8086`](../../FUZIX/Target/rules.8086):

* **`lib`** — `libc8086.a` + `crt0_8086.o` / `crt0nostdio_8086.o` +
  `liberror.txt` + `libm`/`libtermcap`/`libreadline`/`libcurses`, built with
  `ia16-elf-gcc -march=i8086 -Os` and archived with `ia16-elf-ar`
  ([`cmake/UserLib.cmake`](../cmake/UserLib.cmake), source list
  [`cmake/userland-srcs-8086.cmake`](../cmake/userland-srcs-8086.cmake)).
* **`bin`** — programs are compiled with `ia16-elf-gcc` and linked with
  `ia16-elf-ld crt0 objs -lc8086 -lgcc -T `[`lib/link/8086.ld`](../lib/link/8086.ld)
  → **MZ/msdos** executables (the i8086 branch in
  [`cmake/UserBin.cmake`](../cmake/UserBin.cmake)). The maximal set is selected by
  [`configs/ibmpc.cmake`](../configs/ibmpc.cmake) — every registry package minus
  `cc1`/`cc2` (the FCK code generator, which needs per-target codegen objects
  that are not part of an app link): **234 programs build**.

### Disk image (`diskimage` → `hd0.img`)

`ibmpc` has no boot sector upstream, so — unlike v8080 — there is no bootable
floppy. The `diskimage` target therefore packages only the *root-disk* half of
v8080's rule: `mkfs` a FUZIX filesystem, `ucp`-populate it with `/init`,
`/bin/*` (every built program), a `/dev` skeleton, `/etc/*` and
`/usr/lib/liberror.txt`, then `fsck`
([`cmake/diskimage-ibmpc.sh.in`](../cmake/diskimage-ibmpc.sh.in),
`DISKIMAGE_STYLE=rootdisk`). The result, `images/hd0.img`, is the mountable
`hda` image the BIOS-disk driver would read. It depends on `bin`+`tools`, **not**
the kernel, so it builds even while the kernel is still a draft.

```
cmake -B build -DCMAKE_TOOLCHAIN_FILE=cmake/toolchain-i8086.cmake \
      -DFUZIX_CPU=i8086 -DFUZIX_PLATFORM=ibmpc -DFUZIX_CONFIG=ibmpc \
      -DFUZIX_IA16_PREFIX=$PWD/toolchain/ia16-elf-gcc/bin
cmake --build build --target bin        # 234 MZ executables
cmake --build build --target diskimage  # images/hd0.img
```

See [ARCHITECTURE.md](../ARCHITECTURE.md) for where 8086 sits among all CPUs,
[80c188.md](80c188.md) for the embedded 80C188 sibling, and
[fcc8bit.md](fcc8bit.md) for the contrasting 8080/Z80 banked approach.
